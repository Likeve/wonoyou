# INOU 一对一私域聊天技术可行性与产品需求文档

版本 1.0　日期 2026年11月7日　面向产品 设计与研发

## 结论与已确定的产品边界

技术可行。产品定位为可安装到 iPhone 主屏幕的私域聊天 PWA，通过一方输入对方分享的字符串建立好友关系，聊天记录只保存在各自设备。界面采用微信式的信息层级、会话列表和聊天气泡。

用户已确定采用严格本地保存模式：服务器不保存消息正文、附件或它们的密文副本。对方离线时，消息保留在发送方设备，只有双方重新在线且连接可用时才继续投递。不提供云端聊天记录恢复。

“安装”指添加到主屏幕后以独立窗口运行，不是 App Store 原生应用。iOS 主屏幕 Web App 支持通知，但不能把 PWA 当作常驻后台聊天进程。[S1][S2][S4]

### 建议采用的方案

前端 PWA 加本地加密数据库；WebRTC DataChannel 传输消息；轻量服务负责身份公钥、邀请码、好友关系与连接信令；STUN 辅助直连，TURN 在直连失败时实时转发加密流量。服务器不建立聊天消息库，也不提供历史消息 API。[S5][S6]

本方案把“只存设备”落实为服务端不持久化聊天内容；传输过程仍需网络缓冲，TURN 可能接触无法解密的数据包。若未来要求连密文都不得经过服务器，必须关闭 TURN，同时接受部分网络无法聊天。

### 必须接受的体验限制

- 接收方上线但发送方已关闭应用，之前未送达的消息仍然无法抵达；需要双方再次同时在线。
- 锁屏、切到后台、被系统回收后，不承诺持续收发；回到前台重新连接。
- 本地网站数据可能因清理、存储策略或设备丢失而消失。持久化申请不能代替备份。[S3]
- 服务器仍会持有最小必要的账户与关系元数据；“不存聊天记录”不等于“完全无服务器”或“完全匿名”。

### 本文的评估范围

以下技术结论来自官方资料与架构分析，尚未完成双 iPhone 真机原型验证。文中的容量、时延、周期和限额是立项目标或初始建议，需通过原型和内测调整。产品暂名 INOU，可在视觉设计阶段修改。

## 技术可行性与平台限制

| 能力 | 结论 | 实施边界 |
| --- | --- | --- |
| iPhone 主屏幕安装 | 可行 | HTTPS、Manifest、图标、独立窗口及安装引导 |
| 单方字符串加好友 | 可行 | 高随机邀请码作为添加授权，服务端原子核销 |
| 本地查看历史记录 | 可行 | IndexedDB 加密保存，离线可打开已缓存应用 |
| 前台一对一聊天 | 可行 | WebRTC 直连或 TURN 中继，接收端落库后回执 |
| 离线后再投递 | 有条件 | 待发消息在发送端，双方再次在线才投递 |
| 关闭应用后持续收发 | 不承诺 | 不以后台常驻或后台同步作为核心依赖 |
| 锁屏通知 | 有条件 | 主屏幕安装、用户授权、系统与网络允许 |
| 永久不丢记录 | 无法保证 | 需用户导出加密备份；无服务器恢复 |
| 微信式界面 | 可行 | 自有名称、图标和资产，复用熟悉的交互结构 |

### iOS 基线与安装策略

建议首版产品支持 iOS 17 及以上，并以实际测试机型作为支持列表。Web Push 的平台支持起点是 iOS 16.4 的主屏幕 Web App，不代表本产品必须兼容到该版本。[S1] 发布前测试 iOS 17、18 和当期受支持的新版本，不仅测试桌面 Safari。

引导用户用 Safari 打开，按系统分享菜单添加到主屏幕，再从桌面图标进入正式使用。网页预览阶段不生成正式身份，避免把 Safari 标签页与主屏幕实例的数据共享作为前提。iOS 安装入口文案可能随系统版本变化，教程需按真机更新。

### 存储与后台机制

IndexedDB 作为记录和待发队列的主库；Cache Storage 仅保存离线应用资源。调用 Storage API 查询容量并申请持久化，记录是否获批。申请失败仍可聊天，但应提供清晰的备份入口；不宣称“添加到主屏幕后记录永不清除”。[S3][S8]

Service Worker 用于应用缓存和通知事件，不承载常驻 WebRTC 连接。其生命周期由浏览器管理，不能通过定时器、静音音频等手段保证后台永久运行。[S4] 因此，严格本地模式的主要可靠性来自本地队列、前台重连与幂等回执。

## 架构选择与数据流

### 候选方案比较

| 方案 | 服务端内容保存 | 离线投递 | 取舍 |
| --- | --- | --- | --- |
| WebRTC 加 TURN | 不持久化 | 双方同时在线 | 本版推荐；需处理 NAT 与重连 |
| 端到端加密 WebSocket 中继 | 不持久化，仅实时缓冲 | 双方同时在线 | 实现较简单，但全部流量经过服务器 |
| 密文临时邮箱 | 临时保存密文 | 发送方离线后仍可投递 | 不符合已确认的要求，本版排除 |
| 仅 WebRTC 直连 | 不经过消息中继 | 双方同时在线 | 部分网络连接失败，无兜底 |

“本地保存”本身并不强制使用 WebRTC。这里选择它，是为尽量直传内容，同时用 TURN 覆盖直连失败的场景。若原型证明运维或兼容成本过高，可重新评估纯实时加密 WebSocket，但不能悄悄启用密文离线邮箱。

### 组件及职责

- PWA 客户端：界面、设备身份、加密、好友本地缓存、消息数据库、待发队列、备份。
- 身份与关系服务：保存设备公钥、邀请码校验值、好友关系、封禁状态；不保存昵称头像等非必要资料。
- 信令服务：通过 WSS 交换在线状态、SDP 和 ICE 信息；短期内存存在，不写请求正文日志。
- STUN 与 TURN：协助建连或实时转发；使用短期凭证、配额与速率限制，关闭载荷记录。
- 通知服务：可选，发送“有人邀请你上线聊天”一类通用提醒，不携带消息正文或附件。

### 一条消息的完整路径

1. A 输入消息；客户端先在本地事务中保存内容和待发任务，提交成功才清空输入框。
2. A 和 B 都处于可连接状态时，通过信令完成认证与建连；先直连，必要时使用 TURN。
3. A 将应用层加密后的消息通过 DataChannel 发给 B。身份公钥与会话绑定，避免仅信任中继返回的信息。
4. B 验证身份与消息、去重，并将消息及去重状态写入本地事务；事务成功后返回加密 ACK。
5. A 收到有效 ACK 后标为“已送达”。丢失 ACK 时重发同一消息标识；B 不重复展示并补发 ACK。

A、B 任一端不可用时，正文不进入服务器队列。发送方退出前已落库的任务保留；回到前台后重新尝试。服务器重启只能影响连接，不能被当作历史记录来源。

## 安全设计与数据保留

### 身份与通信安全

每个正式安装实例生成设备身份密钥。MVP 一人一个主设备，不以邀请码充当登录密码或消息加密密钥。服务端以挑战签名认证设备，接口检查好友关系与封禁状态。邀请码只授予建联权限。

通信采用经过评审的端到端加密协议实现，支持身份认证、重放防护和会话密钥更新。Double Ratchet 可作为消息加密设计参考，但官方协议文档不等于现成可用的浏览器 SDK；原型必须验证候选库的许可、维护状况、浏览器支持与测试向量，不自行拼装密码协议。[S7]

首次公钥信任存在目录服务被替换的风险：保存首次见到的公钥，并提供双方核对安全码的入口。公钥变化时阻止静默发送，提示重新核验。安全码核验前，不声称已经验证对方真实身份。

### 本地加密与威胁边界

消息、附件、联系人资料和草稿以加密形式存入 IndexedDB。本地随机主密钥由用户解锁口令派生的密钥封装；口令不上传，派生参数在目标 iPhone 上标定并版本化。应用后台超过 60 秒后，下次前台默认要求解锁；内存密钥尽力清理，不承诺物理取证级擦除。

本地加密不能抵御已解锁页面中的恶意脚本，也不能阻止对方截图、导出或系统级窃取。采用严格 CSP、禁止不受信任 HTML、消息链接不自动预览、禁用会话录屏统计、固定依赖和审查发布变更。网站更新被恶意替换仍是 Web 产品的信任边界。

### 服务端数据保留表

| 数据 | 是否允许服务端保存 | 初始保留规则 |
| --- | --- | --- |
| 正文 附件 缩略图及其密文 | 否 | 不写数据库 缓存 日志 备份或推送 |
| 私钥 本地解锁口令 备份口令 | 否 | 仅设备处理 |
| 设备标识与身份公钥 | 是 | 账户存续期间；注销后主库 24 小时内删除 |
| 邀请码校验值与好友关系 | 是 | 有效期内或关系存续期间 |
| SDP ICE 在线状态 | 仅短期内存 | 会话结束即清理；失联超时不超过 5 分钟 |
| 推送订阅地址 | 用户启用时 | 撤销或失效后清理 |
| 运维元数据 | 最小化 | 安全日志建议 7 天；不含载荷 邀请码或会话文本 |

元数据备份建议最长 30 天滚动到期，须对用户说明删除在备份中的延迟。TURN 与信令仍可观察 IP、连接时间和流量大小；直连也可能让对方知道网络地址。不以“零元数据”作为宣传。

## PRD 目标用户与版本范围

### 产品目标

服务已有信任关系的小范围联系人：通过私下分享的字符串快速建立一对一联系，用熟悉的微信式界面聊天，并由用户自己掌握聊天记录。优先满足前台可靠发送、状态诚实可辨、本地可恢复与关系可控制。

成功的最小闭环是：B 分享邀请码，A 单方输入并添加成功；两人打开应用，互发消息；退出后再打开可查看历史；离线发送显示等待；双方重连后只收到一份；导出备份后可恢复已保存的记录。

### 功能分级

| 优先级 | 功能 | 交付范围 |
| --- | --- | --- |
| P0 | iOS 安装与初始化 | 安装引导 本地身份 昵称 解锁口令 |
| P0 | 邀请码加好友 | 生成 复制 输入 核销 撤销 失效处理 |
| P0 | 联系人与关系管理 | 自动双向建联 备注 删除 拉黑 安全码 |
| P0 | 一对一文本聊天 | 多行文本 Emoji 本地历史 草稿与重试 |
| P0 | 图片聊天 | 单张压缩 分块传输 本地查看 |
| P0 | 本地数据管理 | 容量统计 加密导出 导入 删除 |
| P0 | 可观测消息状态 | 待连接 发送中 已送达 失败 |
| P1 | 通用上线提醒 | 用户主动授权 通知不携带聊天内容 |
| P1 | 本地搜索与体验完善 | 本机检索 深色模式 辅助功能优化 |
| 后续 | 语音 文件与迁移 | 经真机验证后单独立项 |

不进入首版：群聊、朋友圈、公众号、红包支付、通讯录上传、手机号搜索、音视频通话、自动云备份、服务器离线消息箱、多设备实时同步、阅后即焚与远程强制删除。

### 首版默认参数

文本每条最多 4,000 个 Unicode 字符；图片原文件不超过 10 MB，处理后目标不超过 2 MB、长边不超过 2,048 像素，不满足则引导重新选择。单次发送一张，暂不支持动图与视频。图片格式解码需做 iPhone 实测，失败显示明确提示。

联系人上限初设 100 人；前台只为当前会话和有待发任务的少量联系人建立连接，并限制并发为 3。以上均为可配置的产品限制，不代表浏览器容量上限。

## PRD 邀请码与好友关系

### 字符串定义

使用系统生成的高随机邀请字符串，不允许用姓名、手机号或短数字充当默认邀请码。建议格式为 INOU 加 26 位 Crockford Base32 随机主体，分组便于复制与输入；随机熵至少 128 位，格式示例只用于设计，不可作为真实授权。

输入时去除首尾空格和展示用连字符，按协议规范大小写和易混字符。前端校验长度与字符集，服务端做实际有效性校验。只允许精确匹配，不提供模糊搜索或枚举用户目录。

### 单方添加流程

1. B 在“我的邀请码”生成并复制代码，默认一次使用、24 小时有效。生成页面明确说明“拿到此码的人可以直接添加你”。B 分享代码即表达该范围的添加授权。
2. A 在“添加好友”粘贴或输入代码，点击“添加”。这是唯一的添加操作，无需 B 再确认。
3. 服务端检查 A 已认证、邀请码有效、不是本人、双方未拉黑；在同一事务中核销代码并建立双向关系。
4. A 本地显示联系人并进入聊天页。B 在线时同步；B 离线时，下次上线出现该联系人。B 无须在线即可完成关系建立，但消息投递仍需双方在线。
5. 昵称、头像通过首次安全连接交换并本地保存；交换前显示临时联系人标识，不因此卡住添加成功状态。

### 边界规则

- 相同用户重复提交成功请求必须幂等返回既有关系；不新增会话。双向同时添加也只生成一条关系。
- 同一个一次性代码被不同人同时提交，只允许一个事务成功。过期、撤销或被别人使用后统一显示“邀请码不可用”。
- 网络超时可安全重试；使用客户端请求标识追踪原子结果，避免“代码已用但关系未建立”。
- B 可以撤销所有未使用代码；这不删除已建立的好友。固定长期邀请码不是首版默认功能。
- 接口初始限制为每设备每分钟 5 次失败尝试，并叠加 IP 与目标码限速、退避及异常封禁；阈值需内测调整。

### 删除与拉黑

删除好友关闭当前关系并停止投递未完成任务，历史默认保留在本机；再次联系需要新邀请码。拉黑同时撤销关系、关闭连接、拒绝新建联与上线提醒；解除拉黑不自动恢复好友。客户端离线拉黑立即在本机生效，服务器规则在网络恢复后同步。

删除历史与删除好友是独立操作。删除本地会话时询问是否一并取消待发消息，防止旧消息随后被意外发出。对方设备上的副本不受本机删除影响。

## PRD 消息状态与投递规则

### 可见状态

| 状态 | 触发条件 | 用户看到的结果 |
| --- | --- | --- |
| 已保存 待连接 | 本地事务完成 但连接不可用 | 时钟图标及“等待双方上线” |
| 发送中 | 安全通道已建立 正在传输 | 进度指示 图片显示百分比 |
| 已送达 | 对方本地事务完成并返回 ACK | 简短送达状态 不表示已读 |
| 等待重连 | 传输中断或 ACK 超时 | 保留气泡 重连后用同一 ID 重试 |
| 发送失败 | 格式错误 关系失效或不可恢复错误 | 红色失败标记 可查看原因 |
| 已取消 | 用户取消尚未确认送达的任务 | 停止后续尝试 不承诺远端未收到 |

不把“已发送到网络”“中继已接收”“本地已保存”展示成“已送达”。ACK 只证明接收端当时成功存储，不证明对方已读，也不保证未来不会清除数据。MVP 不提供已读回执。

### 可靠性与排序

每条消息有不可重复的 messageId、conversationId、senderDeviceId、会话序号、协议版本及创建时间。接收端以发送设备和 messageId 联合去重；消息内容、去重记录和协议状态必须事务一致。文本与图片元信息均做长度与类型校验。

排序以会话序号和接收顺序稳定呈现，不依赖两台手机时钟完全一致；跨发送方并发消息不保证两端获得全球一致排序。设备时间用于展示，明显异常时不影响去重。

断线采用带随机抖动的指数退避，例如 1、2、4、8 秒直至 30 秒；仅在前台且网络可用时重试。单次 15 秒没有 ACK 转为等待重连，不能直接推断对方未收到。待发任务默认不自动过期；超过 24 小时标示“长时间未送达”，用户可取消。

### 图片和容量不足

图片在本地压缩并移除可去除的 EXIF 信息，缩略图同样本地保存与加密传输。按协商的 DataChannel 最大消息尺寸分块，使用背压与文件摘要校验；MVP 断线后可整图重传，以相同附件 ID 去重，不宣称支持完整断点续传。

接收方空间不足时不返回成功 ACK，向发送方反馈可重试的存储错误；保留待发任务并提示。发送方首次本地保存失败时保留输入内容，不清空输入框，不展示虚假的已发送气泡。

## PRD 本地数据与通知

### 数据模型

| 本地实体 | 关键字段与用途 |
| --- | --- |
| Identity | 设备 ID 加密身份私钥 公钥及版本 |
| Contacts | 对方 ID 公钥指纹 本地备注 关系版本与封禁状态 |
| Conversations | 会话 ID 本地最后活动 未读数 草稿 |
| Messages | 消息 ID 发送者 序号 加密内容 状态 附件引用 |
| Attachments | 附件 ID 加密 Blob 媒体类型 大小与摘要 |
| Outbox | 消息 ID 尝试次数 下次尝试时间 ACK 状态 |
| CryptoState | 协议会话状态 版本与防重放信息 |
| Settings | 解锁设置 备份时间 存储持久化结果 |

消息预览、草稿、头像、搜索索引均属于本地隐私数据，不应遗漏在明文缓存中。Service Worker 不缓存聊天 API、邀请码响应或用户正文。数据库升级需事务迁移；迁移失败保留旧数据并阻止破坏性重试。

### 备份与恢复

“我 → 数据与备份”提供容量、上次备份时间和导出入口。首版导出用户选定会话或全部历史与附件的加密档案，由用户自行保存到“文件”等位置；应用不自动上传。用户选择 iCloud Drive 等目录可能触发其个人云同步，应用需在选择前说明。

备份使用单独的备份口令，加密参数和格式版本随文件保存。导入必须先校验完整性、口令与剩余空间，再事务导入，失败不污染现有数据。重复导入按消息 ID 去重。口令丢失无法恢复。

MVP 备份定位为历史档案：不携带设备身份私钥、活动会话密钥或可执行待发任务。换机导入后可查看旧记录，但新设备生成新身份，需要重新加好友；旧记录标明所属旧身份。避免恢复旧协议状态造成密钥回滚或两设备冒用同一身份。

### 通知行为

通知是 P1 可选能力。安装后由用户主动点击开启，拒绝权限不影响前台聊天。发送方可触发限频的“邀请上线”，通知仅显示通用文案，点击后进入应用并等待解锁和重连。发送方此时已离线，接收方也只能看到等待状态。

通知送达受系统和网络控制，不设百分之百送达承诺。严格模式下不把消息密文装进推送载荷，不借助推送服务变相存储聊天内容。iOS 不支持把不可见推送当作长期后台保活方式。[S2]

## PRD 微信式界面与交互规范

### 页面结构

底部三个导航项“聊天、通讯录、我”。聊天列表顶部为应用名称和添加入口；列表行含头像、备注名、本地最后一条消息预览、时间、未读角标和待发提示。通讯录提供添加好友、联系人列表与黑名单入口；“我”提供邀请码、解锁、备份、存储与注销。

聊天页顶部为返回、联系人名和详情入口；中间为消息列表；底部为多行输入框、图片入口、Emoji 与发送按钮。自己的消息靠右、绿色气泡；对方靠左、白色气泡；背景浅灰。连续消息适度合并时间标识，长按支持复制和本地删除。

### 安装与聊天提示文案

首次进入：“聊天记录保存在这台设备。清理数据或更换设备前，请先导出备份。”邀请码页：“持有此邀请码的人可直接添加你。请只分享给想联系的人。”等待状态：“消息已保存在本机，等待双方上线。”

顶部连接提示采用“连接中”“等待双方上线”“连接已断开”，不把心跳缺失直接宣称为对方主动离线。不向用户展示 STUN、TURN、ICE 等实现细节。

### iPhone 交互细节

适配安全区域与动态视口；键盘弹出后输入框不被遮挡，滚动历史时不强制跳到底部。收到新消息且用户正在读旧记录时显示新消息按钮；中文输入法组合输入期间不误触发送。文本框保持至少 16px 避免不必要的输入缩放；长文本、Emoji、图片加载失败均有对应布局。

后台返回先恢复解锁和本地数据，再更新网络状态。升级应用资源时不强制刷新正在传输的会话，允许当前操作结束后更新。

## 研发接口与验收标准

### 建议接口边界

身份注册与挑战认证；邀请码生成、撤销及核销；好友关系增量同步；删除和拉黑；短期 TURN 凭证；WSS 信令；可选推送订阅。好友核销 API 使用 POST 与幂等键，邀请码不放在 URL 查询参数或访问日志中。

服务端不提供消息写入、消息历史查询、附件上传和聊天备份 API。DataChannel 消息帧区分握手、文本、附件、ACK 与错误，协议版本不兼容时停止发送并提示升级。API 认证、限速与关系权限校验覆盖每个接口。

### 功能验收

| 编号 | 测试场景 | 通过条件 |
| --- | --- | --- |
| A01 | 两台 iPhone 安装及首次使用 | 独立窗口启动 身份仅在正式实例生成 |
| A02 | B 离线 A 输入有效码 | A 添加成功 B 下次上线自动出现关系 |
| A03 | 同一码并发核销与超时重试 | 只有一个有效新关系 重试不重复 |
| A04 | 前台互发 100 条消息 | 收件不丢不重；落库成功后才 ACK |
| A05 | B 离线 A 发消息后关闭 | 消息保持待发；仅 B 上线不会凭空送达 |
| A06 | A B 再次上线及丢失 ACK | 最终送达 每条只显示一次 |
| A07 | 锁屏 进后台 杀进程及切网 | 无虚假送达 回前台可恢复待发任务 |
| A08 | Wi-Fi 与蜂窝跨网及强制 TURN | 可建连 或给出明确失败与重试状态 |
| A09 | 存储不足 写入中断 | 不丢输入 不返回成功 ACK 不损坏原库 |
| A10 | 导出 导入 错口令 重复导入 | 内容附件一致 错误不污染 不重复 |
| A11 | 删除 拉黑与公钥变化 | 停止继续发送 规则同步 变更需核验 |
| A12 | 服务端数据库 日志和备份检查 | 找不到正文 附件 或密文消息副本 |

### 性能与验证方式

初始性能目标：已建连且前台网络稳定时，文本送达 ACK 的 P95 小于 1 秒；普通网络首次建连 P95 小于 5 秒；本机 10,000 条文本记录时，会话首屏最近 50 条 P95 小于 500 毫秒。以指定参考 iPhone、网络条件和至少 100 次样本报告，目标不是已有实测结果。

服务端无内容保存需检查应用、代理、APM、错误上报、TURN、缓存、数据库和备份链路。消息可靠性使用故障注入测试：断网、丢 ACK、事务失败、并发重发和进程终止。iOS 后台行为必须用真机验证，不能只依赖模拟器或桌面浏览器。

## 实施计划与上线条件

### 研发周期估算

按 1 名有 WebRTC 经验的全栈工程师、1 名前端工程师，配合兼职设计与测试估算，MVP 约 6 至 8 周；外部密码评审排期和大规模运营能力另算。这是工作量估算，不是报价或交付承诺。

| 阶段 | 预计时间 | 产出与退出条件 |
| --- | --- | --- |
| 技术原型 | 第 1 周 | 双 iPhone 建连 TURN 回执 本地库和安装验证 |
| 身份与好友 | 第 2 周 | 本地解锁 邀请码幂等核销 关系权限 |
| 聊天主链路 | 第 3至4 周 | 文本 图片 队列 重连 去重 微信式 UI |
| 数据管理 | 第 5 周 | 备份恢复 容量管理 删除与封禁 |
| 测试及内测 | 第 6至8 周 | 真机兼容 故障注入 安全检查 修复 |

### 必须先完成的原型验证

两台真机在不同 Wi-Fi 和蜂窝网络互传；强制 TURN 成功；锁屏、后台和系统终止后的状态准确；IndexedDB 持久化申请与配额失败可处理；候选加密库在 Safari 可用；加密档案能通过 iOS 文件选择器导出和重新导入。若任何关键项失败，应调整产品支持范围后再投入完整 UI 开发。

### 成本与容量

持续成本主要包括前端托管、身份及信令服务、小型元数据库、TURN 带宽、域名和监控。无云端消息库仍不等于零服务器成本。TURN 成本按实际经过中继的附件和文本流量估算，不按注册用户数简单推算。

例如，每日 1,000 名活跃用户，每人发送 10 张压缩后 0.5 MB 的图片，日发送量约 5 GB；若 40% 经 TURN，中继转发的图片载荷约 2 GB 每日，另有协议开销。实际计费需区分云商的出站、总流量和跨区口径；这只是容量算例，不是已核实的费用报价。

### 上线门槛与待定参数

P0 验收全部通过；加密实现通过独立评审；服务端无内容持久化检查通过；至少两款 iPhone 和支持版本完成真机矩阵；数据迁移与备份回归通过；公布支持范围和本地保存限制。

下一步需业务方确定正式名称、使用地区、预计活跃用户、单用户图片量、最低 iOS 版本和预算。这些不影响当前“严格本地保存”的架构结论。可先开展一周技术原型，再冻结版本范围与开发报价。
